# Installation

## Host tools

Use a Linux host with QEMU's x86_64 emulator, `qemu-img`, `curl`, Python 3, `sha512sum` and `mkisofs`. Allow 2 GiB of RAM for the guest. KVM is used when available; QEMU falls back to slower software emulation otherwise.

On Debian or Ubuntu:

```sh
sudo apt install qemu-system-x86 qemu-utils genisoimage curl python3
```

Other distributions provide `mkisofs` through `cdrtools` or `genisoimage`. If the launchers were copied without executable permissions, run `chmod +x build.sh run.sh` once.

## Build

```sh
./build.sh 4G
```

The size is total virtual disk capacity, in whole GiB, at least `2G`. Omitting it uses `4G`. The qcow2 disk is sparse and grows on the host as data is written.

The script downloads the official Alpine 3.23.4 BIOS cloud image and verifies a pinned SHA-512 checksum. It caches the base as `.alpine-3.23.4.qcow2` and checks the digest again before using it. The base is never booted directly.

A temporary cloud-init ISO installs the scripts and packages, grows the filesystem, enables disk quotas and unified cgroups, and disables the vendor image's SSH service. The guest reboots, checks the login helpers and ttyd, disables cloud-init, and shuts down. The builder publishes the standalone `webshell.qcow2` only after success. No SSH keys are generated by these project scripts.

Existing disks are never overwritten, including dangling symlinks. To build another VM, move the current disk aside first. Never delete it if you need its accounts or files.

Build work and `console.log` stay in the printed `.build.*` directory for diagnosis. The workspace disk and published disk are hard links to the same file, not independent backups. The ready disk does not need the seed ISO or cached Alpine image to boot.

## Run

```sh
./run.sh
```

Open http://localhost:8080, type `new`, choose a password, and save your UUID. Disconnect and log in with that UUID to return to your permanent home.

The VM stays in the foreground. Only port 8080 is forwarded, bound to host localhost. There is no admin SSH access.

For a clean shutdown, press Ctrl+A, then lowercase `c`, type `system_powerdown`, and press Enter. This sends the guest an ACPI power-button event. Force-killing QEMU can lose data.

## Maintenance and upgrades

Run `test-limits.sh` inside a user session to inspect its cgroup and quota settings. Account homes, password hashes and social records live on the VM disk, not in the source tree.

Changing the repository does not change an existing disk. Guest upgrades, password recovery and failed-account cleanup require offline maintenance. Back up the powered-off disk first. A fresh build is a new VM, not an account migration.

The guest currently uses external ext4 user quotas. The tested Alpine kernel enforces these, but reports their deprecation. Migrate to internal quotas before upgrading to a kernel that removes support.

Keep this for a trusted small group. It does not isolate users from the shared guest kernel or network. Do not expose plain HTTP signup to the Internet.
